###### Abstract.

Agentic software systems are increasingly used in development workflows,
where changes to the model, prompt, scaffold, tools, or execution
environment require repeated testing. Selecting a subset of tests can
reduce testing costs while providing quick estimates of agent
performance or exposing failures early to support failure analysis.
Although test case selection (TCS) has been studied for deep neural
networks and LLM code models, prior work does not directly address
agentic systems and often requires model information that is unavailable
for proprietary agents.

This paper presents the first empirical study of black-box TCS for
agentic software systems. We treat each benchmark task as a test case
and adapt black-box regression-testing techniques by redefining their
selection criteria over task descriptions, metadata, code fragments, and
embedding representations. We also propose new strategies that estimate
task difficulty using heuristic features or independent LLM-as-judge
assessments. Our proposed and adapted strategies select tasks without
executing the target agent or using past results.

We evaluate fourteen selection strategies, including random sampling,
and an additional historical-data baseline on ten AI agent benchmarks,
including SWE-bench Verified, with 12 to 101 agents per benchmark. We
assess Success Rate estimation and early failure detection. No single
strategy dominates both objectives. Adapted black-box regression-testing
strategies are most effective for Success Rate estimation, with Category
Partition obtaining the lowest median error on five of the ten
benchmarks at the 20% task budget. LLM-as-judge selection is more
effective for early failure detection. For GPT 5.2 Codex on SWE-bench
Verified, Category Partition executes 100 instead of 500 tasks and
reduces execution cost from \$225 to \$47, with an absolute error in
Success Rate estimation of 0.8 percentage points. At the same task
budget, LLM-as-judge selection detects nearly twice as many failures as
random sampling: 53.0% of selected SWE-bench Verified tasks reveal
failures, compared with 27.4% for random sampling.

## 1. Introduction

AI agents increasingly write code, resolve programming issues, interact
with the web, and perform a wide range of software engineering tasks.
Their performance is typically evaluated using standard benchmarks that
assess success in completing predefined tasks. As these agents evolve,
modifications to the underlying model, prompt, orchestration, tools, or
execution environment require continuous testing (Asgari et al., 2026b).
However, executing a complete benchmark can be costly (Hasan et al.,
2026): each task may require multiple calls to large language models
(LLMs), tool interactions, and code execution. These costs increase with
benchmark size. For example, SWE-bench Verified contains 500
tasks (Jimenez et al., 2024), while SWE-Bench Pro contains 607 (Scale
AI, 2025). Selecting a subset of tasks could reduce these costs and
provide faster feedback after changes by requiring fewer agent
executions, provided that the selected tasks support accurate
performance estimation or help reveal failures early.

A similar challenge has long existed in software testing. As test suites
grow, executing every test after each software change becomes
increasingly expensive (Yoo and Harman, 2012). Test case selection (TCS)
addresses this issue by selecting a subset of tests (Rothermel et al.,
2001; Elbaum et al., 2002). More recently, TCS has been studied for deep
neural networks (DNNs), primarily on image-classification tasks, and for
LLM code models on classification tasks such as vulnerability detection,
clone detection, and technical debt prediction (Asgari et al., 2026a).
These studies consider two objectives: estimating overall model
performance from a sample of inputs and selecting inputs that reveal
failures early.

Applying TCS to agentic systems introduces new challenges. Many existing
deep neural network (DNN) and LLM test-selection techniques depend on
information from the system/model under test, such as confidence scores,
uncertainty estimates, activations, coverage, or internal
representations (Aghababaeyan et al., 2024; Tian et al., 2018;
Abbasishahkoo et al., 2025; Asgari et al., 2026a). However, such
information is unavailable for closed-source models or black-box agents.
Furthermore, agent evaluation typically involves generative tasks where
the agent interacts with tools and environments to complete a task,
rather than predicting a single class label.

In this paper, we formulate benchmark evaluation for agentic software
systems as a test case selection problem. Each benchmark task is a _test
case_, each candidate agent is a _system under test_, and an
unsuccessful task is a _failure_. Following prior test-selection
studies (Asgari et al., 2026a; Guerriero et al., 2024; Asgari et al.,
2025), we consider two objectives: estimating an agent’s full-benchmark
Success Rate from a subset of tasks and exposing failures early for
failure analysis. To the best of our knowledge, this is the first
empirical study of black-box TCS for agentic software systems. We adapt
seven black-box regression-testing techniques by redefining their
selection criteria over task descriptions, metadata, code fragments, and
embedding representations. These techniques include category
partitioning, boundary-value selection, textual diversity, clustering,
and adaptive random selection. We also propose six novel task-difficulty
strategies: two use heuristic features, and four use independent
LLM-as-judge assessments. These thirteen strategies require neither
execution of the target agent nor recorded outcomes from the same or
other agents.

Together with random sampling, they form the fourteen primary strategies
evaluated in our study. We also include Historical Mid-Range, a baseline
adapted from prior work on predicting agent leaderboard
rankings (Ndzomga, 2026). Unlike our strategies, this baseline uses
recorded outcomes from other agents, excluding the target agent’s
outcomes. The study covers ten public AI agent benchmarks encompassing
repository-level software engineering (Jimenez et al., 2024; Yang et
al., 2025; Scale AI, 2025), competitive programming (Shi et al., 2024),
terminal use (The Terminal-Bench Team, 2025), tool-using dialogue (Yao
et al., 2024), computational reproducibility (Siegel et al., 2024),
general assistant tasks (Mialon et al., 2023), and web browsing (Xue et
al., 2025). For each strategy, we assess how accurately the selected set
of tasks estimates each agent’s full-benchmark Success Rate and how many
failures it reveals at task budgets of 10%, 20%, and 50%.

The results show that the two objectives benefit from different
selection strategies. For Success Rate estimation, adapted black-box
regression-testing strategies yield the strongest results, with Category
Partition achieving the lowest median estimation error on five of the
ten benchmarks. For early failure detection, LLM-as-judge
difficulty-based selection proves more effective, prioritizing failing
tasks earlier in the selected subset across the evaluated benchmarks.

Our results also suggest that evaluation costs can be reduced in
practice. For DeepSeek V3.2 on SWE-bench Multilingual, Category
Partition evaluates 60 of 296 tasks, reducing execution cost by
approximately 82%, from \$114 to \$20, with an absolute error in Success
Rate estimation of 0.8 percentage points. On SWE-Bench Pro, when testing
GPT-5 within SWE-agent with a 250-turn limit, LLM-as-judge selection
detects approximately 42% more failures than random sampling at the same
20% task budget: 91.7% of selected tasks reveal failures, compared with
64.5% for random sampling. These examples illustrate how task selection
can reduce the cost of performance estimation and detect more failures
within the same task budget.

This paper offers the following contributions:

- •
  We formulate limited-budget evaluation of agentic software systems as
  a test case selection problem and, to the best of our knowledge,
  present the first empirical study of black-box TCS for agentic systems
  and generative agent tasks.
- •
  We adapt seven strategies from black-box regression testing and
  propose six task-difficulty strategies that select tasks without
  executing the target agent. We evaluate these strategies against
  random sampling and a historical-performance baseline.
- •
  We conduct an empirical study across ten public agent benchmarks,
  evaluating the strategies for Success Rate estimation and early
  failure detection at three task budgets using 12 to 101 agents per
  benchmark.
- •
  All code and results are released to support replication.

## 2. Background and Related Work

Regression testing aims to reduce the cost of executing large test
suites after software changes (Yoo and Harman, 2012). Many regression
testing techniques rely on white-box information, such as statement or
branch coverage collected from previous executions. Black-box
techniques, instead, use only information available from the test inputs
and are therefore more practical when source code, instrumentation, or
prior coverage data is unavailable. Henard et al. (Henard et al., 2016)
showed that black-box techniques based on input characteristics and
diversity can be competitive with coverage-based techniques. Related
black-box testing methods include category partitioning (Ostrand and
Balcer, 1988), where tests are derived from observable partitions of the
input space, and Adaptive Random Testing (ART) (Chen et al., 2010),
where each new test is selected to be far from the tests already
selected according to a distance metric over the input domain. ART is
motivated by the observation that failures often cluster in the input
space, so diverse inputs can exercise different behaviors earlier.

Black-box regression testing has also used textual information to
compare and select tests (Feldt et al., 2016). In
information-retrieval-based regression testing, program changes are
treated as queries and tests as documents to retrieve; models such as
TF-IDF, LSI, and LDA are then used to rank tests by their textual
similarity to changes (Peng et al., 2020) or to other tests in the
suite (Aman et al., 2018). More broadly, machine-learning-based
regression testing has used test-case text to construct representations
for unsupervised methods, including clustering and topic modeling (Pan
et al., 2022).

Our setting differs from conventional regression testing because our
test inputs are benchmark tasks rather than conventional executable test
cases, such as JUnit tests. Each test is an agent task: a prompt
together with the context, files, repository state, tools, and success
criterion provided by the benchmark. Executing a test means invoking the
agent on that task and observing whether it reaches the expected
outcome. Thus, there is no executable test body comparable to a JUnit
method; the executable procedure is the agent run, and the assertion is
provided by the benchmark oracle or success criterion. We therefore
re-interpret black-box regression testing criteria using task-side
information, including task descriptions, benchmark metadata, code
snippets, test names, and embedding representations.

Test selection for deep models. Test case selection has been studied for
deep models to reduce labeling and execution costs while supporting
performance estimation and early failure detection (Ma et al., 2020).
Selection criteria include uncertainty, surprise adequacy, coverage,
sampling, and diversity (Ma et al., 2020; Kim et al., 2019; Guerriero et
al., 2024). Their effectiveness depends on the objective:
uncertainty-based criteria often favor failure discovery, whereas
representative samples better support performance estimation. Many
techniques require model-side information, such as probabilities,
logits, or hidden-layer activations, which may be unavailable for
proprietary agents or difficult to define consistently across systems
combining LLMs, tools, memory, and execution environments.

Recent work has extended test case selection to LLMs. Clotho (Yoon et
al., 2026) identifies inputs likely to reveal failures using LLM hidden
states and a labeled reference set, before output generation. Asgari et
al. (Asgari et al., 2026a) re-examined DNN selection techniques on LLMs
performing code-related classification tasks, such as clone detection,
vulnerability detection, and technical-debt prediction. Several criteria
in these studies rely on model-side information, such as predictive
probabilities or hidden-layer representations. Our setting differs: we
study agentic systems that solve generative, interactive, and often
multi-step benchmark tasks. We focus on task-related criteria computed
before executing the target agent, including task features, textual and
embedding representations, and independent task-difficulty judgments,
without requiring recorded agent outcomes.

Predicting agent leaderboard rankings. Ndzomga studies reduced benchmark
suites for predicting agent leaderboard rankings (Ndzomga, 2026). The
approach uses historical per-task pass rates from previously evaluated
agents to identify tasks of intermediate difficulty, motivated by item
response theory. Tasks that are solved by almost all agents or by almost
none of them carry little information for ranking, whereas
mid-difficulty tasks are expected to better discriminate among agents.
The resulting reduced suite is evaluated by how well it preserves the
ranking of agents that would be obtained from the complete benchmark.
Instead of finding a subset of tasks that can predict the overall
ranking of agents, we search for a subset that facilitates predicting
agent performance with a limited budget. The selected prefix is assessed
by how accurately it estimates the target agent’s full-suite Success
Rate and how many of its failures it exposes early. We adapt the
historical mid-range idea as a baseline by computing each task’s pass
rate over all agents in the benchmark except the target agent, then
prioritizing tasks whose pass rate is closest to 0.5. This
leave-one-agent-out version keeps the original principle of selecting
discriminative mid-difficulty tasks while avoiding the target agent’s
own outcomes when constructing the ordering.

## 3. Test Case Selection for AI Agents

Following prior work on test selection for LLMs for code (Asgari et al.,
2026a), we treat each benchmark task as a test case: an input on which
the agent is executed and its success or failure is assessed. Tasks may
include issue reports, programming problems, terminal instructions, web
tasks, or tool-use scenarios. Given a benchmark with tasks
$`T=\{t_{1},\ldots,t_{n}\}`$ and a budget of $`k`$ tasks, each strategy
selects a subset $`S\subseteq T`$ with $`|S|=k`$. Selection follows the
strategy’s criterion until the budget is reached. For strategies that
select tasks sequentially, the selected set contains the first $`k`$
tasks chosen. These sets support two objectives: estimating the agent’s
full-benchmark Success Rate and exposing failures early.

### 3.1. Test Selection Techniques

We describe seven strategies adapted from black-box regression testing
and six novel strategies that estimate task difficulty before executing
the agent, together with random sampling as a baseline. Historical
Mid-Range, an additional baseline requiring outcomes from other agents,
is described in Section 4.2. Unless stated otherwise, ties are resolved
by the original benchmark order: if tasks $`t_{i}`$ and $`t_{j}`$
receive the same score and $`i<j`$, then $`t_{i}`$ is selected first.

#### 3.1.1. Random sampling.

Random is our feature-agnostic baseline (Asgari et al., 2025; Henard et
al., 2016). For a budget of $`k`$ tasks, it samples $`k`$ tasks
uniformly without replacement. This baseline tests whether task
information, such as text, metadata, embeddings, or difficulty
estimates, improves over chance. It is especially strong for Success
Rate estimation because random samples are unbiased estimators of the
full-benchmark Success Rate, but it does not target difficult or
failure-prone tasks and is therefore less suited to early failure
detection.

#### 3.1.2. Adapted Black-box Regression Techniques.

The second family adapts black-box regression-testing ideas to agent
benchmarks. In traditional black-box testing, selection uses observable
properties of the test inputs rather than coverage or internal
information from the system under test. We apply the same principle to
agent tasks: the input is the benchmark task given to the agent,
including its natural-language description, code snippets, metadata,
test names, repository or task category, and other contextual fields.
The following strategies reinterpret black-box selection criteria over
these task-side properties.

Task length is a single-feature baseline. It computes the number of
characters in the task text available before execution, including the
instruction, problem statement, hints, contextual fields, and any code
snippets that appear in them. The strategy selects longer tasks first,
using length as a proxy for task complexity: longer tasks may contain
more requirements, constraints, code fragments, or environmental
details, and may require more context management, exploration, or tool
use from the agent.

Boundary Value adapts boundary-value testing to agent tasks. Traditional
boundary-value testing selects inputs near the edges of an input domain
because such inputs are often more likely to expose faults. Since agent
benchmarks do not provide explicit numeric input domains, we define
boundaries over task-input features available before execution, such as
task length, number and length of code spans, number of lines, token
counts, prose entropy, and the presence of tracebacks or exception
names. For each feature $`f_{j}`$, we compute the median
$`\widetilde{f_{j}}`$ over the benchmark and assign each task a
normalized distance from it:
$`d_{j}(t_{i})=|f_{j}(t_{i})-\widetilde{f_{j}}|/(\mathrm{MAD}(f_{j})+\epsilon)`$,
where $`\mathrm{MAD}`$ is the median absolute deviation. The boundary
score is $`\mathrm{Boundary}(t_{i})=\max_{j}d_{j}(t_{i})`$. Tasks are
selected in decreasing score, so tasks that are unusually short, long,
code-heavy, sparse, or otherwise extreme in at least one observable
feature are selected earlier. The method does not use oracle information
or agent outcomes.

Category Partition adapts the category-partition method (Ostrand and
Balcer, 1988). The original method partitions the input domain using
categories and choices derived from the specification. We apply the same
principle to benchmark tasks by building categories from task
information available before execution. When available, we use benchmark
variables such as task type, domain, repository, language, or difficulty
label; we also derive simple textual variables, such as whether the task
contains a traceback, mentions an exception or warning, and its length
quartile. For example, in SWE-bench-style repair tasks the repository
can define a category variable, while in other benchmarks the task type
or domain can play the same role. Each non-empty combination of
variables defines a task category. The method sorts tasks within each
category by decreasing length and then cycles over categories, selecting
one task from each at a time. Early selected sets therefore cover
different task types, domains, textual patterns, and length ranges.

TF-IDF Diversity (Original and Code) adapts diversity-based black-box
regression testing to agent tasks (Feldt et al., 2016; Peng et al.,
2020). We evaluate two variants that differ only in how they construct
the task document. TF-IDF Diversity (Original) uses the original task
text, including the instruction, problem statement, hints, context
fields, and any existing code. TF-IDF Diversity (Code) uses the same
document but additionally appends extracted code blocks and inline code
spans, increasing the contribution of code-related tokens to the
representation without introducing new information. Both variants use
the same representation and selection procedure. We lowercase documents,
tokenize them into word unigrams and bigrams, filter out English stop
words, and represent them as TF-IDF vectors with sublinear
term-frequency scaling. We do not apply stemming or lemmatization
because identifiers, library names, and error names may carry useful
information. Diversity between tasks $`t_{i}`$ and $`t_{j}`$ is computed
using cosine distance,
$`d(t_{i},t_{j})=1-\frac{\mathbf{x}_{i}\cdot\mathbf{x}_{j}}{\|\mathbf{x}_{i}\|\,\|\mathbf{x}_{j}\|}`$,
where $`\mathbf{x}_{i}`$ and $`\mathbf{x}_{j}`$ are their TF-IDF
vectors. Selection starts with one uniformly random task; each
subsequent task maximizes its minimum distance to previously selected
tasks. Neither variant uses agent outcomes or benchmark oracle
information.

Adaptive Random adapts adaptive random testing (Chen et al., 2010) to a
task-embedding space. In ART, each new test is chosen to be far from the
tests already selected. Here, task descriptions are embedded with
CodeT5+ (Salesforce/codet5p-110m-embedding) (Wang et al., 2023), reduced
to 10 dimensions with UMAP using cosine distance, and normalized before
selection. The method then applies the same farthest-from-selected rule
as TF-IDF Diversity, but computes distances between task embeddings
rather than TF-IDF vectors. Thus, early selected tasks cover different
regions of the learned task representation.

Round Robin adapts clustering-based test selection and
prioritization (Pan et al., 2022). The method clusters the same task
embeddings used by Adaptive Random with $`k`$-means and then cycles over
the non-empty clusters, selecting one task from each cluster before
returning to the same cluster. Within each cluster, tasks are ordered by
the sum of two standardized task-input features: prose-token entropy and
the presence of a traceback. For a benchmark with $`n`$ tasks, we set
$`k=\max(4,\mathrm{round}(0.06n))`$. This makes the number of clusters
grow with benchmark size while retaining at least four clusters on small
benchmarks (Aloise et al., 2017). The value of $`k`$ is fixed before
observing any agent outcome and is used only to obtain a coarse
partition of the task space.

#### 3.1.3. Task-Side Difficulty Estimation

The third family estimates task difficulty before executing the target
agent. The rationale is that, under a limited testing budget, harder
tasks may be more useful for exposing failures early. These strategies
do not run the target agent and do not use agent outcomes. They use only
task-side information available before execution, such as task
descriptions, code fragments, metadata, or independent LLM-as-judge
assessments. Each strategy constructs a benchmark-level task ordering,
and the selected set at budget $`k`$ is the first $`k`$ tasks in that
ordering. The same selected sets can therefore be reused for every agent
evaluated on the benchmark.

Difficulty Score estimates five aspects of task difficulty from the task
input. File, function, line-number, and traceback mentions reduce
estimated localization difficulty. File-path mentions, code blocks, and
text length approximate the expected change size; prose entropy, text
length, and the proportion of code approximate reasoning difficulty.
Counts of bullet points, numbered steps, and words expressing
requirements (e.g., “must”) or requested outputs (e.g., “write”)
approximate validation complexity. Reproduction-related words and code
blocks reduce estimated reproducibility difficulty. The method
standardizes features within each benchmark and combines them into five
factor scores using predefined weights, documented in the replication
package. It then standardizes the factor scores using $`z`$-scores and
sums them with equal weight, selecting tasks with higher total scores
first.

Difficulty Score with Diversity uses the same difficulty score but
combines it with diversity. The method first divides the tasks into four
difficulty bands using the quartiles of the difficulty-score
distribution within the benchmark. The bands are visited from hardest to
easiest. Within each band, the method applies the Round Robin procedure
over the task-embedding clusters, selecting one task from each non-empty
cluster per cycle. Thus, the selected set favors difficult tasks while
avoiding many near-duplicate tasks.

LLM-as-Judge uses an independent LLM to estimate the overall difficulty
of each task before the target agent is executed. For each task, the
judge is asked to assign one difficulty score on a four-point scale. The
judge receives only task-side information available before target-agent
execution, together with a benchmark-type description of what the task
asks the agent to do and how success is determined. It does not receive
target-agent outcomes, leaderboard information, benchmark labels, gold
answers, oracle tests, or other outcome information. Tasks are selected
in decreasing judged difficulty, with ties resolved by the original
deterministic task order.

LLM-as-Judge with Diversity uses the same one-dimensional LLM difficulty
judgment but adds a diversity step. Tasks are first grouped by their
judged difficulty score, from score 4 to score 1. The method visits
these groups from hardest to easiest. Within each group, it applies
cluster round-robin selection using task-embedding clusters, so that
selected tasks remain diverse among tasks judged to have the same
difficulty. This keeps the focus on hard tasks while reducing repeated
selection of similar tasks.

Factor-Based LLM-as-Judge asks an independent LLM to estimate difficulty
along several predefined factors rather than giving only one overall
score. For each task, the judge assigns a four-point score to each
factor separately. The factors depend on the type of task. For coding
and software-repair tasks, they include localization hardness, expected
code-change size, reasoning hardness, validation-test complexity, and
reproducibility hardness. For more general agent tasks, they include
information gathering, action complexity, reasoning and planning,
verification difficulty, and execution fragility. In both cases, the
factor scores are standardized within the benchmark using $`z`$-scores
and summed with equal weight. Tasks are selected in decreasing composite
difficulty.

Factor-Based LLM-as-Judge with Diversity combines the factor-based
difficulty score produced by LLM-as-Judge with diversity. The method
first computes the composite difficulty score from the standardized
factor scores. It then divides tasks into four difficulty bands using
the quartiles of this composite-score distribution and visits the bands
from hardest to easiest. Within each band, it applies the Round Robin
procedure over the task-embedding clusters, selecting one task from each
non-empty cluster per cycle. The selected set therefore favors tasks
judged difficult along multiple factors while spreading the budget
across different task topics or regions.

prompting procedure, the generated judgment scores, and the
leakage-sensitivity analysis.

## 4. Empirical Evaluation

This section describes the experimental protocol of our empirical study.
We structure the study around two research questions, one for each
evaluation objective established in the test-selection literature (Hu et
al., 2024): Success Rate estimation and early failure detection.

We investigate the following research questions:

- •
  RQ1: How effective are selection strategies at estimating an agent’s
  full-benchmark Success Rate under a limited task budget?
- •
  RQ2: How effective are selection strategies at detecting an agent’s
  failures early under a limited task budget?

### 4.1. Benchmarks

We use ten public agent benchmarks covering issue resolution (Jimenez et
al., 2024; Yang et al., 2025; Scale AI, 2025), competitive
programming (Shi et al., 2024), terminal use (The Terminal-Bench Team,
2025), tool-using dialogue (Yao et al., 2024), computational
reproducibility (Siegel et al., 2024), general assistant tasks (Mialon
et al., 2023), and web browsing (Xue et al., 2025). We obtain published
outcomes from the benchmark releases and the Holistic Agent Leaderboard
(HAL) (Stroebl et al., 2025).

Table 2 summarizes the ten benchmarks, which contain 45 to 607 tasks.
For each benchmark, published evaluation results are available for 12 to
101 agents and record whether each agent successfully completed each
task. Here, an agent denotes an evaluated system configuration rather
than a distinct underlying model: entries differ in their model,
scaffold, tools, or execution limits. We retain the configurations
associated with the published results without modifying or rerunning
them. We use these outcomes to assess Success Rate estimation and
failure detection on the tasks selected by each strategy, without
rerunning the agents. None of the fourteen primary strategies uses agent
outcomes to select tasks.

The benchmarks also differ in difficulty for the AI agents: the median
failure rate across agents ranges from 27.2% on SWE-bench Verified to
76.7% on CORE-Bench Hard. Because benchmark sizes differ, we evaluate
selection at 10%, 20%, and 50% of the available tasks rather than using
fixed task counts. SWE-bench Mini contains 50 tasks from SWE-bench
Verified. We retain it as a separate setting because it includes a
different set of evaluated agents and represents a smaller evaluation
suite, while acknowledging that the two benchmarks overlap.

### 4.2. Baselines

We compare our strategies with two baselines. Random sampling is a
standard baseline in regression testing (Rothermel et al., 2001; Elbaum
et al., 2002) and in test selection for deep neural networks (Asgari et
al., 2026a). We use it to assess whether the other strategies estimate
Success Rate more accurately or detect more failures within the same
testing budget.

Historical Mid-Range. Historical Mid-Range is an external baseline
adapted from prior work (Ndzomga, 2026). The original method selects
benchmark tasks whose historical Success Rate across agents falls within
a mid-difficulty range (30–70%), with the goal of identifying tasks that
are informative for distinguishing among agents. Since our setting
instead requires selecting tasks under a limited evaluation budget for a
single target agent, we adapt this idea into a complete task ordering.

For each target agent $`a`$, we compute the historical Success Rate of
each task $`t`$ using the outcomes of all other agents on the same
benchmark,
$`p_{t}^{(-a)}=\frac{1}{|A|-1}\sum_{r\in A,\;r\neq a}Y_{r,t}`$, where
$`Y_{r,t}=1`$ if agent $`r`$ successfully completes task $`t`$ and $`0`$
otherwise. Tasks are then ordered by $`|p_{t}^{(-a)}-0.5|`$ in ascending
order, such that tasks with historical Success Rates closest to 50% are
selected first. This converts the original mid-range criterion into a
full ordering from which the first $`k`$ tasks can be selected for any
evaluation budget.

To avoid leakage, we exclude the target agent’s own outcomes when
constructing its ordering and use them only afterward to evaluate the
selected tasks. Unlike our fourteen primary strategies, Historical
Mid-Range therefore requires historical outcomes from other agents on
the same benchmark. We consequently treat it as an external baseline
rather than one of the fourteen primary strategies, while including it
in our statistical comparisons.

### 4.3. Experimental Setup and Metrics

We evaluate the strategies described in Section 3 on the benchmarks
introduced in Section 4.1. For each benchmark and target agent, each
strategy generates an ordering of the benchmark tasks using only
information available prior to evaluating the target agent.

##### LLM judges.

The main study uses Sonnet judgments. Newly collected judgments use
claude sonnet-5 with high reasoning effort, tools disabled, no web
access, and no conversation history. To assess sensitivity to the judge
model and possible benchmark contamination, we repeat the four judge
strategies using gpt-4o-mini-2024-07-18, with temperature 0 and a
maximum output length of 512 tokens. Its stated training cutoff predates
the release of several evaluated benchmarks, allowing us to examine
whether the results also hold with an older judge. Section 6 discusses
this analysis, and Section 7 addresses its limitations. The five judged
factors depend on task type: coding tasks use localization hardness,
expected change size, reasoning hardness, validation complexity, and
reproducibility hardness; other tasks use information gathering, action
complexity, reasoning and planning, verification difficulty, and
execution fragility. Scores are standardized per benchmark and summed
equally. Newly collected responses must contain the required integer
scores from 1 to 4; invalid responses are retried, and missing scores
are not imputed. Prompts, available raw outputs, validated scores,
settings, and selection scripts are included in our replication package.

##### Task budgets and repetitions.

Following previous TCS studies on deep learning systems and LLM code
models (Guerriero et al., 2021; Guerriero et al., 2024; Asgari et al.,
2025; Asgari et al., 2026a), we evaluate each strategy at budgets of
10%, 20%, and 50% of benchmark tasks, rounded up to the nearest integer.
These budgets represent small, moderate, and large partial evaluations,
allowing us to assess whether performance patterns remain consistent as
more tasks are evaluated. We run deterministic strategies once and
repeat strategies involving random or seed-dependent steps 100 times
with different seeds.

##### Outcome classification.

We use published binary task outcomes where available. For fractional
scores or success rates across repeated runs, a task counts as
successful at 50% or above.

##### Success Rate estimation error (RQ1).

Success Rate is the proportion of tasks that an agent completes
successfully according to the benchmark’s success criterion, such as
passing the required tests for a software-repair task or completing the
requested web interaction. For a target agent $`a`$ and budget $`k`$,
let $`\hat{R}_{a}(k)`$ denote its Success Rate on the $`k`$ selected
tasks and $`R_{a}`$ its Success Rate on the complete benchmark. The
estimation error is defined as

```math
\mathrm{SccErr}_{a}(k)=\left|\hat{R}_{a}(k)-R_{a}\right|.
```

Lower values indicate more accurate estimates. An error of zero means
that the selected set and the complete benchmark yield the same Success
Rate.

##### Failures found (RQ2).

For a target agent $`a`$ and budget $`k`$, we count the selected tasks
on which the agent does not satisfy the benchmark’s success criterion.
Higher values indicate that more failures are detected within the same
task budget $`k`$.

##### Aggregation and statistical analysis.

For randomized strategies, each target agent contributes the mean metric
value across the 100 repetitions. For each benchmark, strategy, and
budget, we report the median of the per-agent values and their
interquartile range (IQR). The statistical tests use the per-agent
values, not the benchmark-level medians.

For each metric and budget, we compare each technique family together
with Random and Historical Mid-Range using the Friedman test at
$`\alpha=0.05`$ (García et al., 2009). Strategies are the compared
treatments, and benchmark–agent pairs from the ten benchmarks are the
matched blocks. When Friedman identifies significant differences, we
apply the Nemenyi post-hoc test to determine which strategies differ
significantly (García et al., 2009). Lower mean ranks indicate lower
estimation error or more detected failures, depending on the objective.
Two strategies differ significantly when the difference between their
mean ranks exceeds the Nemenyi critical distance, which accounts for all
pairwise comparisons within each family and its baselines. This
combination of Friedman and post-hoc tests is widely used for comparing
algorithms across multiple problems, including applications in
search-based software engineering (Devroey et al., 2023; Panichella,
2021), benchmarking studies (Japkowicz and Shah, 2011), and a recent
study on test selection for LLMs for code (Asgari et al., 2026a).

We evaluate all strategies at the 10%, 20%, and 50% budgets. Due to
space limitations, Sections 5.1 and 5.2 present detailed results for the
20% budget only. Complete results for all budgets are available in our
replication package, and the effects of different budgets are discussed
in Section 6.

Extending test selection to agentic and generative tasks. Test selection
under limited budgets has traditionally focused on predictive neural
models, especially deep neural networks and vision classification tasks
(Guerriero et al., 2024; Abbasishahkoo et al., 2025; Kim et al., 2019;
Pietrantuono and Russo, 2018), emphasizing performance estimation and
early failure detection as key evaluation objectives(Aghababaeyan et
al., 2024; Guerriero et al., 2021; Tian et al., 2018; Zhou et al.,
2020). A previous study extended these objectives to large language
models (LLMs) for code, addressing classification-based software
engineering tasks such as vulnerability detection, clone detection, and
technical debt prediction (Asgari et al., 2026a). The findings indicated
that representation-based approaches were more effective for Success
Rate Estimation, whereas uncertainty-based approaches were more
effective for early failure detection.

This study advances the investigation of these two objectives by
focusing on software engineering agents and generative tasks. Unlike
classification settings, agent benchmarks assess whether an agent can
complete a task through a sequence of actions and generated outputs. The
predictive probabilities and internal model representations utilized by
traditional deep neural network (DNN) test-selection techniques are not
directly available or comparable across agents. Consequently, this
study’s strategies rely on information about the benchmark tasks
themselves, including textual properties, embeddings, task categories,
and difficulty estimates.

This is the first study to investigate both Success Rate estimation and
early failure detection through task selection for software engineering
agents and generative agent benchmarks. Across ten benchmarks, our
results show that both objectives can be supported under limited task
budgets, but they favor different categories of selection strategies.

Success rate estimation versus failure detection. The results reveal a
clear distinction between the two evaluation objectives. Strategies that
perform well for Success Rate estimation generally differ from those
effective for early failure detection. For Success Rate estimation,
black-box strategies such as Category Partition, Adaptive Random, and
Random perform well, as they do not explicitly prioritize tasks based on
estimated difficulty. In contrast, early failure detection benefits from
difficulty-based selection, particularly the LLM-judge strategies. This
distinction aligns with the differing goals of the two objectives.
Estimating the full-benchmark Success Rate requires the evaluated tasks
to approximate the complete benchmark effectively. In contrast,
prioritizing difficult tasks intentionally places those with a higher
estimated failure risk earlier in the ordering. This helps reveal
failures earlier, but the resulting prefix can be less suitable for
estimating performance over the complete benchmark. Conversely, a more
representative ordering can provide an accurate estimate of the overall
Success Rate without necessarily prioritizing failure-prone tasks.

Results across evaluation budgets. Figure 5 shows how Failures Found and
SccErr change as the evaluation budget increases from a small fraction
of the benchmark to the full benchmark. We show two benchmarks for each
objective: SWE-bench Verified and USACO for failure detection, and
SWE-bench Multilingual and SWE-Bench Pro for SccErr. We compare Random
with the best black-box strategy and the best difficulty-based strategy
at each budget so that the best strategy can change along the curve; the
dots mark the 10%, 20%, and 50% budgets. Because we choose the best
strategy at each budget, both family curves represent their best
performance. The pattern observed at the 10%, 20%, and 50% budgets holds
across the full budget range on these benchmarks. For failure detection,
the best difficulty-based strategy finds more failures than the best
black-box strategy and Random at almost every budget. For SccErr, the
best black-box strategy has the lowest error, while the best
difficulty-based strategy rarely improves on Random. As the budget
approaches 100%, all strategies converge.

The statistical comparisons based on performance averaged across the
10%, 20%, and 50% budgets show a similar overall ranking pattern
(Figure 7 and Figure 8). Category Partition, Boundary Value, and
Adaptive Random obtain the best mean ranks for Success Rate estimation
among the regression-testing methods and baselines. Factor-Based
LLM-as-Judge variants remain best-ranked for failure detection, while
Random remains best-ranked for Success Rate estimation among the
difficulty-based methods and baselines.

Impact on cost savings. Reducing the number of evaluated tasks can
substantially decrease agent evaluation costs. Table 5 illustrates this
using SWE-bench Verified and SWE-bench Multilingual. At the 20% task
budget, the evaluated strategies cost between \$41 and \$80 on SWE-bench
Verified, compared with approximately \$225 for the complete benchmark.
On SWE-bench Multilingual, the corresponding costs range from \$31 to
\$61, compared with approximately \$191 for the complete benchmark.

However, task budget and monetary cost are not equivalent. Different
strategies may execute the same number of tasks at a given budget, but
the selected tasks can have varying execution costs. For example, at the
20% budget on SWE-bench Verified, Category Partition costs \$47, while
Factor-Based LLM-as-Judge costs \$80. Factor-Based LLM-as-Judge detects
substantially more failures, with a median of 53.0 compared to 29.0 for
Category Partition, but it also executes a more expensive set of tasks.
This demonstrates that selection influences not only which failures are
observed but also the monetary cost of the evaluation.

For Success Rate estimation, Category Partition offers a distinct
trade-off. At the 20% budget, it costs \$47 on SWE-bench Verified and
\$31 on SWE-bench Multilingual, compared to \$45 and \$37 for Random. At
the same time, its SccErr is lower on both benchmarks: 0.018 vs. 0.033
on Verified, and 0.033 vs. 0.042 on Multilingual. In these examples,
selection improves the Success Rate estimate at a lower cost on
Multilingual and a slightly higher cost on Verified.

Also, figure 6 shows the cost savings of each strategy at the 10%, 20%,
and 50% budgets. At the 20% budget, several black-box strategies
(Category Partition, TF-IDF, and Adaptive Random) save about 80-83% of
the cost. The judge-based strategies save less (about 68–73%) because
the tasks they select are more difficult and tend to be more expensive
to run.

The cost of the LLM-as-judge. The strategies also differ in the cost of
constructing their orderings. Random and most black-box strategies
require no LLM calls, whereas LLM-judge strategies require difficulty
estimates for the benchmark tasks prior to agent evaluation.

Table 6 reports the cost of producing these judgments across the ten
benchmarks. Using Claude Sonnet 5, the judgments cost approximately
\$45.50 in total based on the recorded token usage. Using GPT-4o mini,
the corresponding cost is approximately \$0.93. Importantly, each task
is judged once, and the resulting difficulty scores can then be reused
when evaluating different agents on the same benchmark. The cost of
constructing the ordering can therefore be shared across multiple agent
evaluations. The utility of this additional step depends on the
evaluation objective. For early failure detection, LLM-judge strategies
provide clear improvements over Random and most black-box strategies,
making the additional difficulty information valuable. For Success Rate
estimation, judge-based strategies generally offer no corresponding
advantage, as simpler black-box strategies already achieve low
estimation error. The additional judging step is therefore most
beneficial when the objective is to expose failures early.

Judge model sensitivity: GPT-4o mini. The main experiments use Claude
Sonnet 5 as the judge. To test sensitivity to this choice, we repeat the
four LLM-judge strategies with GPT-4o mini, keeping the rest of the
empirical methodology unchanged. Figure 8 compares the difficulty-based
strategies using the two judges. We omit the methods adapted from
regression testing because they do not use judge scores and their
results remain unchanged. For failure detection, the Task-Side
Difficulty Estimation strategies rank above Random and Historical
Mid-Range, while for Success Rate estimation, Random obtains the best
mean rank. The connecting bars link strategies that are not
statistically distinguishable under the Nemenyi test. This analysis also
reduces the concern that benchmark memorization drives the results.
GPT-4o mini has a stated knowledge cutoff of October 2023, predating the
release of several evaluated benchmarks, yet the overall pattern remains
similar. This does not rule out possible training-data exposure for
every benchmark.

Implications for benchmark maintenance and agent development. The TCS
methods can help curators examine benchmark composition and decide where
to add new tasks. For example, Category Partition divides SWE-bench
Verified into 89 partitions, of which 30 contain only one task, while
the five largest contain 35.4% of the benchmark. For Claude 4.5 Sonnet,
Django tasks without traceback or exception names have a failure rate of
15.3% in the shortest length group (9/59 tasks), compared with 50.0% in
the longest group (7/14); the full-benchmark failure rate is 28.6%.
Curators could add diverse tasks to sparsely populated or empty
categories relevant to the benchmark’s scope, or construct further tests
for categories with high observed failure rates.

For agent developers, selecting tasks from a development or validation
suite can reduce the cost of testing changes to the model, prompt,
harness, tools, or execution environment. Inspecting the selected
failures can help identify problems such as incorrect tool invocation or
repository setup errors and guide harness improvements. On a held-out
test set, selection can provide quick performance estimates and identify
failures for inspection.

## 7. Threats to Validity

Construct validity. We represent each task outcome as binary success or
failure. For HAL results aggregated across repeated runs, a task counts
as successful if the agent solves it in at least 50% of runs. Fewer than
1.5% of HAL task–agent outcomes are fractional, so this conversion
affects few outcomes. For TerminalBench 2.0, more than 50% of trials
must pass. About one third of its task–agent results contain both
successful and failed trials, so a different threshold could affect
full-benchmark Success Rate and failure counts. We apply the same
conversion rule to all strategies within each benchmark but do not
evaluate alternative thresholds. Our difficulty-based strategies also
assume that task information available before execution helps estimate
difficulty. This assumption may not hold when difficulty depends mainly
on tool behavior or execution conditions. Although Factor-Based
LLM-as-Judge detects more failures than Random on all ten benchmarks at
the 20% budget (Table 4), these results may not generalize to other
settings.

Internal validity. Some strategies require benchmark-specific
adaptations because the available task information differs across
benchmarks. When a required field is unavailable, we use an alternative
based on available task information, as described in Section 3, without
using agent outcomes. Historical Mid-Range differs from the fourteen
primary strategies because it uses other agents’ outcomes, while
excluding those of the target agent. LLM-as-judge strategies depend on
the judge model and prompt. We repeat all four variants with GPT-4o mini
and obtain a similar overall pattern, but do not systematically vary the
prompts. Judges may have encountered benchmark tasks during training.
GPT-4o mini’s stated training cutoff of October 2023 predates several
benchmark releases, reducing this concern but not ruling out the data
leakage concern completely. We rely on published agent evaluation
results and do not independently reproduce their outcomes. Errors in
benchmark oracles, execution environments, or reported results could
therefore affect our findings.

External validity. We evaluate ten public agent benchmarks covering
software engineering, competitive programming, terminal interaction,
tool use, computational reproducibility, general assistant tasks, and
web navigation. The results may not generalize to other domains,
languages, or benchmarks. The benchmarks vary considerably in their
numbers of tasks and evaluated agents. SWE-bench Mini overlaps with
SWE-bench Verified and therefore does not provide an independent sample.
The reported savings use recorded execution costs for the selected
tasks; costs in subsequent evaluations may differ because agent
behavior, API prices, and execution conditions can change.

## 8. Conclusion and Future Work

AI agents are increasingly used for software engineering, but evaluating
them on complete benchmarks can be costly. To the best of our knowledge,
this is the first empirical study of black-box test case selection for
agentic software systems. We evaluated fourteen pre-execution selection
strategies and a historical-performance baseline across ten public agent
benchmarks. Our results suggest that strategies adapted from black-box
regression testing are more effective for estimating an agent’s
full-benchmark Success Rate, while LLM-as-judge difficulty strategies
detect more failures earlier. These overall patterns remained consistent
across the different evaluated budgets.

Task selection can also substantially reduce evaluation costs. At the
20% budget, Category Partition reduces the cost of evaluating GPT 5.2
Codex on SWE-bench Verified from \$225 to \$47 (a 79% reduction) and
DeepSeek V3.2 on SWE-bench Multilingual from \$114 to \$20 (an
approximately 82% reduction). The absolute error in Success Rate
estimation is 0.8 percentage points in both cases. For early failure
detection, Factor-Based LLM-as-Judge detects 53.0 failures for GPT 5.2
Codex on SWE-bench Verified at the 20% budget, compared with 27.4 for
Random, nearly twice as many within the same task budget. Overall, these
results show that selecting benchmark tasks according to the evaluation
objective can support performance estimation and failure detection at a
fraction of the full execution cost.

Future studies can explore additional measures of task difficulty, such
as cyclomatic complexity when task inputs include source code.
Alternative embedding models, including general-purpose text encoders
and other code models, can help assess how task representations affect
selection. Beyond the TF-IDF methods evaluated here, other
information-retrieval models could capture textual similarity (Peng et
al., 2020). Alternatives to Round Robin could allocate selections
proportionally to cluster size or maximize distance from already
selected tasks. Finally, evaluating these approaches on new agents and
benchmarks can further assess their generalizability.
